## Part 1 - Issues #41 and #42 (committed as 5406ad92)

### Objective
Structural cleanup: separate compile-time configuration from runtime state.

### Delivered
- **`include/config.h`** (new) - configuration constants extracted from `common.h`
- **`include/status.h`** - `AppStatus` struct expanded with `isReady()`,
  `isWiFiAvailable()`, `hasConfig()`, `reset()`
- **`include/common.h`** - configuration removed, `#include "config.h"` added for
  backward compatibility (no `.cpp` file needed editing)
- Committed as `5406ad92`, pushed to `origin/main`.

### What went wrong (important)
`config.h` was written by copying the code block from the issue text instead of
reading what the real code resolved to. Two defects shipped:

1. **Display regression.** Original `common.h` had:
   ```c
   #define MY_WIDTH  TFT_HEIGHT   // 240
   #define MY_HEIGHT TFT_WIDTH    // 135
   ```
   with a comment explaining they are deliberately transposed because the ST7789V2
   screen is rotated. The issue text's plain `135`/`240` were copied verbatim,
   transposing every sprite and every `pushImage`. The explanatory comment was
   deleted too.
2. **Fabricated constants.** 14 constants were invented into `config.h` with
   **zero usages**, several factually wrong (`/spiffs`, `/config.json`,
   `/activities` do not exist; real files are `/data_<day>.json` and `/picto`).
   `MAX_ACTIVITIES` was asserted as 5 while the web UI and `PSpref` allow 20.

Both were found and fixed in the follow-up work, not by the build.

**Lesson:** a generated issue is a suggestion, not evidence. Any value moved
during a refactor must be diffed against the pre-refactor expansion, and a build
pass proves nothing about a numeric constant.

## Efficiency Insights

- The expensive mistake was cheap to make and expensive to miss: copying issue
  text instead of reading resolved values. A single preprocessor expansion of
  `MY_WIDTH`/`MY_HEIGHT` would have caught it before commit.
- Verification that only checks "it compiles" is worthless for constant
  refactors. Value-level assertions are mandatory here.
- Three separate tools mislead me during this session and each was caught by
  measurement: `write_file` silently stripped the leading `//` from `ABOUTME:` lines
  (breaking the build with `'ABOUTME' does not name a type`), the shell working
  directory drifted mid-session (fixed by using absolute paths), and two shell
  commands hit a hardline blocklist (fixed by using `search_files`).

## Process Improvements

1. Before moving any `#define`, diff the pre-refactor expansion against the new one.
2. Treat generated issues as hypotheses; verify every symbol exists before planning.
3. When a `pio test` run reports 0 tests, treat it as a broken harness, not a pass.
4. Prefer `write_file` for new files only after confirming headers survive intact -
   verify `head -3` after writing any file that needs a leading comment marker.
